# Shop counter UX

The primary user is a **single shop owner**, often standing at a counter with a customer waiting, sometimes juggling a barcode scanner, sometimes with a queue behind them. This is not an office worker filling out a form at leisure. Every friction point in the billing/receiving flow costs real time with a real customer standing there. Back-office screens (Reports, Settings, Stock Ledger, Suppliers/Customers/Mechanics CRUD) don't need this level of urgency — this skill is about the live-transaction screens: New Sale, New Purchase, and anything that touches them.

## Core rules

1. **Minimize clicks/keystrokes per line item, always.** If a workflow can be done by typing a number and pressing Enter versus clicking a dropdown, opening it, scrolling, and clicking an option — prefer the keyboard path. This is why scan-to-add (see [[barcode-integration]]) auto-selects the oldest batch and fills the price instead of making the owner pick both manually, and why every `<select>` in the app is now a type-to-filter searchable-select (see [[ui-visual-conventions]]) instead of a long scroll-to-find dropdown.
2. **Enter moves forward, not sideways or back.** `base.html` now has a global rule: pressing Enter in a text/number/date/email/tel/search input or a select advances focus to the next field in the form, and only submits once there's no next field left. This is the app's actual answer to "keyboard-first" — new counter-screen fields don't need special handling to get this, it's automatic, **except** for anything that wants to intercept Enter for its own purpose (the barcode scan box); that case must explicitly stop the event from reaching this handler — see [[ui-visual-conventions]] and [[barcode-integration]].
3. **Autofocus the field the owner will use next**, and return focus there after every action that doesn't need their attention elsewhere. A barcode scan box that loses focus after each scan (because focus moved to whatever new row/element was inserted) breaks the "just keep scanning" flow and forces a mouse click mid-transaction — always focus the scan box explicitly after handling the scan, never assume the browser will leave it there.
4. **Never block the transaction with a confirm() dialog or modal for routine actions.** Removing a line item, adding a line, or moving to the next field should never need a "are you sure?" — that's for review-and-print pages (viewing/deleting a finalized invoice), not for building one. Save destructive confirmations for things that can't be undone after commit (e.g. deleting a Product/Supplier/Customer/Mechanic, which already flashes an error via the deletion guards rather than a JS confirm — keep it that way).
5. **Defaults should assume the common case, not the edge case.** Oldest-batch-first is already the default in the sales form's batch selector ([templates/sales/form.html:186](../../../templates/sales/form.html#L186)) — new selectors on counter pages should follow the same "the thing the owner needs 90% of the time is pre-selected" principle rather than defaulting to a blank/prompt state. Remember the searchable-select gotcha when doing this: after setting `selectedIndex`/`value` programmatically, call `.refreshSearchable()` too (see [[ui-visual-conventions]]), or the visible text won't match the actual selection.
6. **Errors during a live transaction must be recoverable without losing entered data.** If a sale fails validation (e.g. a batch doesn't have enough `remaining_qty`), the owner should not have to re-type the whole invoice — flash the specific problem line and let them fix just that, not reset the form. Check this whenever adding new validation to `routes/sales.py`/`routes/purchases.py`.
7. **Design for the screen actually in use.** This is a Windows desktop/laptop app running locally — not a phone. Don't add mobile-first patterns (bottom nav bars, swipe gestures, hamburger-only navigation) to counter screens; the existing horizontal navbar with full labels is correct for this context. Bootstrap's responsive grid is still fine to keep for the rare case of a tablet, but design and test against a normal laptop screen first.
8. **Print output is a real physical artifact, not just a webpage.** Invoices ([templates/sales/view.html](../../../templates/sales/view.html)) and future barcode labels get handed to a customer or stuck on a shelf — check print layout (via the browser's print preview, not just the screen render) whenever touching a page with a print button, since screen and print layout diverge easily (nav/buttons hidden via `.no-print`, but table column widths and page breaks are not automatically checked).
9. **Assume the internet may be down at any moment.** Every asset a counter-critical page needs (CSS, JS, fonts) must load locally from `static/vendor/`, never from a CDN — see [[ui-visual-conventions]] for where Bootstrap already lives after this was fixed. A billing screen that partially fails to render because a CDN request timed out would be the single worst-case UX failure for this app's stated purpose, so treat any new CDN reference as a regression, not a shortcut.
10. **Never call a counter-screen change done without driving it in a real browser first.** The billing/receiving flows are exactly where a silent JS failure (lost focus, a console error breaking the scan-to-add handler, a 404'd asset) costs the owner the most — a customer standing there while the page misbehaves. Follow the chrome-devtools MCP verification steps in [[ui-visual-conventions]] before reporting any change to New Sale, New Purchase, or their shared JS as finished — source-reading alone does not count as verification here.

## Where this doesn't apply

Reports, Settings, CSV export/backup, and the CRUD list/form pages for Suppliers/Customers/Mechanics are used at leisure, not mid-transaction — normal Bootstrap form/table conventions (see [[ui-visual-conventions]]) are sufficient there without needing scan-box autofocus or zero-confirm-dialog treatment.
