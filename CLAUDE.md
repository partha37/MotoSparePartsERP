# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Flask-based inventory, billing, and tracking ERP for a two-wheeler spare parts shop (multi-brand: Honda, TVS, Bajaj) in Tamil Nadu. Single-shop, single-user, offline-first — runs locally, no cloud hosting, no JS build step. Server-rendered pages only.

## Commands

```
# first-time setup
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
set FLASK_APP=app.py
flask db upgrade

# run the app (development — auto-reload, debug console)
venv\Scripts\activate
python app.py
# open http://127.0.0.1:5000 — first visit prompts you to create the shop-owner login

# after changing models.py
set FLASK_APP=app.py
flask db migrate -m "describe your change"
flask db upgrade
```

There is no test suite, linter, or build step configured.

**Before verifying any change in a real browser, use `qa/qa_server.py` — never click through the live app on real data.** `python qa/qa_server.py` runs the app against a disposable copy of `instance/erp.db` on port 5099 (with the Excel mirror and cloud backup both isolated too), and exposes `/qa-auto-login` to skip the login form. See [qa/README.md](qa/README.md) for usage/flags and exactly what it isolates — don't hand-roll a one-off isolation script, extend this one instead.

**Daily/production use is `serve.py` (waitress), not `python app.py`.** `app.py`'s dev server has `debug=True` (auto-reload, interactive debugger) — fine while developing, wrong to leave running for real billing. `start.bat`/`stop.bat` wrap `serve.py` for the shop owner (double-click to start/stop, console window = the running process). See [DEPLOYMENT.md](DEPLOYMENT.md) for the full setup (including the `.env`-based `SECRET_KEY` `config.py` now loads via `python-dotenv`, silent/hidden startup options, and backup guidance) — don't duplicate that detail here, just be aware `python app.py` is a dev-only path when reasoning about how the app actually runs day to day.

## Architecture

**App factory + blueprints.** `app.py` defines `create_app()`, initializes `db`/`migrate`/`login_manager`/`csrf` from `extensions.py`, and registers one blueprint per domain from `routes/` (auth, dashboard, products, brands, suppliers, purchases, customers, mechanics, sales, stock, reports, settings). Each blueprint owns its own templates under `templates/<blueprint>/`.

**Single `models.py`** holds all SQLAlchemy models — no per-domain model files. Key relationships:
- `Product` only stores the *cost* side of pricing: `mrp` and `actual_discount_pct`/`actual_discounted_price` (cost from distributor). There is deliberately no stored selling price — MRP is GST-inclusive by law, so selling price is decided per sale, not fixed on the product. Call `product.recalc_prices()` after changing `mrp`/`actual_discount_pct` — it's not automatic on assignment. `margin_per_unit` (best-case margin if sold at full MRP) and `is_low_stock` are computed properties, not columns.
- **`Brand`** is a shared master list (`routes/brands.py`) — `Product.brand_id`/`Supplier.brand_id` are FKs into it, replacing what used to be free-typed `brand` text on each. Both models expose a `brand_name` property (`self.brand.name if self.brand else ""`) for templates/exports that want the string. Deleting a `Brand` is blocked (flashed error, app-layer check like other deletion guards) if any `Product`, `Supplier`, `CustomerBrandDiscount`, or `MechanicBrandDiscount` references it. `Product.brand_id` is required at the application layer (`routes/products.py::new_product`/`edit_product` flash an error and re-render if missing) even though the column itself stays `nullable=True` — that's for legacy rows recorded before this rule existed, not an invitation to skip the check on new code paths.
- **Customer/Mechanic discounts are per-brand, not a single flat rate.** `CustomerBrandDiscount`/`MechanicBrandDiscount` are separate tables (one row per customer-or-mechanic + brand pair) — the old flat `Customer.discount_pct`/`Mechanic.discount_pct` columns are gone. Use `customer.discount_for_brand(brand_id)` / `mechanic.discount_for_brand(brand_id)` to look up a rate, or `routes/sales.py::_attach_discount_maps()` to attach a `.brand_discount_map` ({brand_id: pct}) to a list of customers/mechanics for the sales form's client-side JS. Like before, this is a checkout-time convenience only — `routes/sales.py` still accepts whatever `selling_price` the form submits per line, nothing is enforced server-side.
- **`ProductCategory` is a second, optional master list on `Product` (`Product.category_id`, mirrors `Brand`/`brand_id` exactly), and `CustomerCategoryDiscount`/`MechanicCategoryDiscount` hold an *adjustment* per contact + *brand* + category that is added on top of the plain brand rate — it does not replace it.** e.g. a mechanic with Tvs 13% plus a "Tvs + Fiber `-2`" row bills Tvs fiber parts at **11%**; the stored number is a delta, commonly negative (less discount than the brand rate), so nothing here may clamp it to >= 0. The adjustment is deliberately brand-specific rather than a blanket per-category rate — the same category is worth a different delta across brands. `Customer.discount_for_product(brand_id, category_id)`/`Mechanic.discount_for_product(...)` implement this: brand rate + the pair's adjustment when one exists, otherwise the plain brand rate unchanged — which covers both products with no category (`category_id is None`, i.e. "Normal", deliberately not a row in `ProductCategory`) and categorized products whose pair simply hasn't been configured. Both sides `round(..., 2)` the sum, since 13 + -2.1 lands on 10.899999999999999 in binary floating point. `routes/sales.py::_attach_discount_maps()` attaches both `.brand_discount_map` ({brand_id: pct}) and `.category_discount_map` ({"brand_id:category_id": pct}, string keys since these cross into JS as JSON) in one pass, since the form always needs both. The precedence check itself happens client-side in `templates/sales/form.html`'s `currentDiscountForProduct()` (and the duplicated copy in `templates/sale_returns/exchange.html`), keyed off each product `<option>`'s `data-brand-id`/`data-category-id`. The Brand+Category table on the Customer/Mechanic forms names its brand picker `category_brand_id[]`, not `brand_id[]`, so its values don't get mixed into `_sync_brand_discounts()`' own `getlist("brand_id[]")`. Like brand discount, this is checkout-time convenience only, still editable per line, nothing enforced server-side.
- `Purchase`/`PurchaseItem` (stock-in) and `Sale`/`SaleItem` (stock-out) are header/line-item pairs. Saving either must also update `Product.current_stock` directly and insert a matching `StockMovement` row — this isn't automatic (see `routes/purchases.py::new_purchase` and `routes/sales.py::new_sale` for the pattern to follow).
- **Recording a purchase updates the product's "current" cost/MRP/GST rate — latest purchase wins.** `Product.update_cost_from_purchase(purchase_price, new_mrp=None, gst_rate=None)` is called for every purchase line, making that line's price the product's new `actual_discounted_price`/`actual_discount_pct` (and `mrp`/`gst_rate` too, if provided). This is purely a "what to show as the product's headline cost/MRP" convenience — the real per-purchase numbers live on `PurchaseItem` (see below) and are never overwritten.
- **Purchase-side GST: `PurchaseItem.purchase_price` is GST-inclusive — that's the real per-unit cost of the batch, and it's what every downstream consumer (`Product.actual_discounted_price`, stock valuation, `reports/profit_margin`, discount-vs-MRP math) already treats as "the cost."** The New Purchase form has the owner enter `price_before_gst` (what the distributor actually quoted, pre-tax) and a per-line `gst_rate` (defaults to 18%, editable) — the server computes `purchase_price = round(price_before_gst * (1 + gst_rate / 100), 2)` and stores all three; `PurchaseItem.discount_pct` (vs MRP) is derived from that GST-inclusive `purchase_price`, not the raw quoted price. `PurchaseItem.gst_amount`/`gst_amount_per_unit` and `Purchase.gst_total`/`pre_gst_total` are computed properties for display (Purchase view/invoice, the GST Paid report at `/reports/gst`). `price_before_gst`/`gst_rate` are nullable — a one-off backfill script (not a migration, same pattern as the batch-tracking backfill below) ran once against the live DB to retroactively set `gst_rate=18%` on every pre-existing `PurchaseItem` (using its then-current `purchase_price` as `price_before_gst`, then recomputing `purchase_price` GST-inclusive) and to refresh every `Product`'s current cost/`gst_rate` from its latest batch — this changed historical cost/margin figures app-wide by design, at the shop owner's explicit request, and isn't something to redo or reference as a migration. **No GST math exists on the Sales side** (see below) — this is purchase-cost-only.
- **`Purchase.total` includes invoice-level extra charges, not just goods cost — `Purchase.items_total` is the goods-only subtotal if you need that instead.** `Purchase.delivery_charge` is a single always-present fixed-label field (nullable, defaults to `None`/0); `PurchaseCharge` (`purchase_id`, `label`, `amount`) is a free-form multi-row table for anything else on the invoice the owner wants to record — round off (can be negative — no `min=0` on that input, unlike every other purchase amount field), incidental charges, stock handling charges, etc. — added via the New Purchase form's "Additional Charges" section (`+ Add Charge`, mirrors the item-line add/remove pattern but with plain text+number inputs, no product picker). `Purchase.charges_total` = `delivery_charge` + `sum(charges)`; `Purchase.total` = `items_total + charges_total` — this is what's shown as "Grand Total" on the form/invoice and what the Purchases list "Total" column sorts/filters on (`routes/purchases.py::list_purchases` joins a `PurchaseCharge` aggregate subquery alongside the existing `PurchaseItem` one). Existing purchases from before this feature have no `delivery_charge`/`PurchaseCharge` rows, so `Purchase.total` for them is unchanged — no backfill was needed here, unlike the GST bullet above.
- **`PurchaseItem` doubles as a sellable stock batch — this is a real FIFO batch-tracking system, not just a cost-display convenience.** Each purchase line has its own `remaining_qty` (decremented as sales draw from it), `mrp_at_purchase` (that batch's MRP snapshot, `None` for pre-batch-tracking rows), and a computed `stock_number` (`ddmmyyyy-id`, e.g. `26072026-14`) and `effective_mrp` (`mrp_at_purchase` if set, else falls back to the product's current `mrp` for legacy rows). `Product.current_stock` remains the aggregate total (still updated in parallel on every purchase/sale) — `sum(batch.remaining_qty for batch in product.purchase_items)` should always equal it going forward. `routes/sales.py::_attach_available_batches()` builds the oldest-first sellable batch list per product for the sales form; `routes/sales.py::new_sale` requires every sale line to reference a specific `purchase_item_id` and blocks the whole sale if that batch doesn't have enough `remaining_qty` (no silent cross-batch borrowing). Batches from before this feature existed were backfilled once (`remaining_qty` reconciled oldest-first against each product's actual `current_stock`, since past sales weren't tracked per-batch) — that backfill already ran against the live DB and isn't part of the migration itself, so don't expect to find it in `migrations/versions/`.
- `StockMovement` is the single source of truth for day-wise tracking (`routes/stock.py`) — every stock change must write one row here with `type` (`purchase_in`/`sale_out`/`adjustment`/`return`) and a signed `qty`.
- Mechanic-wise/customer-wise reporting is just `Sale` filtered by `mechanic_id`/`customer_id` — there's no separate tracking table. `routes/reports.py::customer_wise`/`mechanic_wise` are the summary lists (one row per contact, date-range filtered); clicking a row (via `tr[data-href]`, skipped for the "Walk-in"/"No mechanic" bucket since it isn't a real contact) drills into `routes/reports.py::_contact_detail()` (shared by the `customer_detail`/`mechanic_detail` routes), which adds day/week-grouped purchase history, a per-product breakdown, and profit/discount KPIs for that one contact — see [.claude/skills/ui-visual-conventions/SKILL.md](.claude/skills/ui-visual-conventions/SKILL.md) for the chart/table toggle these and the summary pages use.
- **No GST math anywhere in Sale/SaleItem.** `SaleItem.line_total` is just `qty * selling_price` and `Sale.total` is the sum of those — MRP already includes GST, so nothing is added on top. `Product.gst_rate` still exists as a reference/master-data field (e.g. for filing) but is not read anywhere in the sales flow. Don't reintroduce a GST addition here without checking with the user first — this was a deliberate correction of an earlier bug.
- **Only the single most-recently-created Sale/Purchase can be edited after saving — `Sale.is_editable`/`Purchase.is_editable` (`models.py`) gate this, both routes and templates.** A `Sale` is editable only while it's the latest by id, has no `SaleReturn` against it, and has at most the one checkout-time `Payment` (no installment, no refund) — anything beyond that means real cash/return history would be destroyed by an edit. A `Purchase` is editable only while it's the latest by id and zero stock has been sold from any of its batches (no `SaleItem.purchase_item_id` pointing at one of its `PurchaseItem` rows) — otherwise `remaining_qty`/`current_stock` can't be safely unwound. `routes/sales.py::edit_sale`/`routes/purchases.py::edit_purchase` (both `GET/POST /<id>/edit`) reuse `sales/form.html`/`purchases/form.html` in an edit mode (`sale`/`purchase` passed to the template instead of `None`) and implement editing as **reverse-then-recreate, not a diff**: `_reverse_sale_side_effects()`/`_reverse_purchase_side_effects()` undo the original entry's stock/StockMovement/Payment footprint (restoring `batch.remaining_qty`/`Product.current_stock`, deleting the old `StockMovement` rows found by `reference_type`+`reference_id` since that table has no FK/relationship, deleting old `SaleItem`/`PurchaseItem`/`PurchaseCharge`/`Payment` rows), then the exact same validation+creation logic `new_sale`/`new_purchase` already use (`_validate_sale_form`/`_validate_purchase_form`, shared by both routes) re-applies the submitted form data — all in one transaction, updating the existing row's mutable fields rather than inserting a new one, so `id`/`invoice_no`/`created_at` never change. `_validate_sale_form` takes an `editing_sale` param specifically so batch-availability validation adds back whatever qty *this same sale* currently holds from a batch before checking it — otherwise editing a sale that had fully drawn down a batch would incorrectly fail as "not enough stock" against its own already-reduced `remaining_qty`. **Known limitation**: editing a Purchase and removing a product's only line entirely leaves that `Product`'s `mrp`/`actual_discounted_price`/`gst_rate` at whatever this purchase last set them to — there's no stored cost history to revert to (same root cause as `update_cost_from_purchase`'s existing "last write wins" behavior) — `edit_purchase` flashes a warning naming the affected product(s) rather than silently leaving stale-looking data, but doesn't attempt to fix it.
- `Sale.invoice_no` is generated as `INV-{id:05d}` via `routes/sales.py::_next_invoice_no()`.
- **`Sale.customer_id` being `NULL` is ambiguous on its own — "no customer entered" and "explicitly Walk-in" are different things, distinguished by `Sale.is_walkin`.** The New Sale/Exchange form's Customer picker has three states: a real customer, `-- None --` (true placeholder, `value=""`, `is_walkin=False`), or `Walk-in` (`value="walkin"`, `is_walkin=True`) — read `Sale.customer_display` (`"-"` / `"Walk-in"` / the customer's name) rather than re-deriving this with `sale.customer.name if sale.customer else 'Walk-in'` in a new template, which would misreport every `is_walkin=False` sale as Walk-in. Every sale recorded before this column existed defaults to `is_walkin=True` (migration `server_default`), matching how they already displayed under the old, single-state logic — no separate backfill. This is a per-sale display distinction only; the aggregate "Walk-in"/"No mechanic" bucket in `routes/reports.py::customer_wise`/`_contact_detail` still groups both together, since neither is a real contact to drill into.
- **`Sale.amount_paid` and `Sale.balance_due` are computed properties, not columns.** `Payment` is a separate table — one row per installment paid against a `Sale` (`sale_id`, `date`, `amount`, `payment_mode`, `note`). `Sale.amount_paid` sums that sale's `payments`; `Sale.balance_due` is `total - amount_paid - return_credit` (see below) and **can go negative**, meaning a refund is owed back to the customer. `routes/sales.py::new_sale` inserts an initial `Payment` row if `amount_paid > 0` was submitted at sale time; `routes/sales.py::record_payment` adds further installments later and rejects (flashed error) any payment that would push `amount_paid` past `total`. Payments never touch stock — no `StockMovement` row, no `Product.current_stock` change. `reports/outstanding-dues` (`routes/reports.py::outstanding_dues`) lists every `Sale` with `balance_due > 0`. `routes/sales.py::record_refund` handles the negative-balance case, logging cash actually handed back as a **negative-amount** `Payment` — `amount_paid` is a sign-agnostic sum, so this needed no other code changes to settle `balance_due` back to 0.
- **Returns/exchanges: `SaleReturn`/`SaleReturnItem` (`routes/sale_returns.py`), separate from `Sale`/`SaleItem`.** A `SaleReturn` holds one or more `SaleReturnItem` lines against a specific original `SaleItem`, each with its own `condition` (`resellable` or `defective`). Only `resellable` items restock — `condition == 'defective'` means the item is gone from the customer but deliberately *not* added back to `Product.current_stock`/`PurchaseItem.remaining_qty`, and no `StockMovement` row is written for it either (a `resellable` return does write one, `type="return"`). `SaleItem.returned_qty`/`returnable_qty`/`net_qty`/`net_line_total` derive from `sale_item.return_items` and are what reporting should read instead of the raw `qty`/`line_total` — every revenue/profit report (`routes/reports.py`) already nets these out so numbers aren't overstated after a return; `Sale.total` itself is never rewritten and stays the original invoice amount. `Sale.return_credit` sums refund value counting toward that sale's balance: its own standalone returns, plus any returns *applied* to it via the exchange flow. **Exchange** (`routes/sale_returns.py::new_exchange`) is a return + a brand-new `Sale` created in the same request/transaction — the return's `SaleReturn.applied_to_sale_id` points at that new sale instead of being left as a standalone credit against the original, so the customer's refund is netted against what they're buying instead of paid out separately. The new-sale half reuses `routes/sales.py`'s `_attach_available_batches()`/`_next_invoice_no()` so it behaves identically to a normal sale (still requires a `purchase_item_id` per line, still blocks on insufficient `remaining_qty`). `routes/reports.py::returns_report` (`/reports/returns`, "Returns & Defectives") is the one deliberate exception to "reports net returns out" above — it exists specifically to show the raw resellable-vs-defective breakdown (by product and over time, plus the full return/exchange history list) that the netted figures elsewhere never surface.
- **The "Reorder Report" lists the entire product catalog, not just low-stock items — the URL/route/template are still named `low_stock` for stability, don't be misled by the name.** `routes/reports.py::low_stock` (`/reports/low-stock`) queries every `Product`, tags each with `.stock_status` (`out`/`low`/`ok`) and `.needs_reorder` via `_attach_stock_status()`; only out-of-stock/low-stock rows start pre-checked in the template, but any product can be checked. "Add to Purchase" posts the checked ids as `?product_ids[]=...` to `purchases.new_purchase`, which reads them via `_prefill_products_from_request()` and pre-fills that many line items (each with a `.suggested_qty` = `reorder_level - current_stock`, min 1) on the New Purchase form — MRP/Purchase Price are deliberately left blank there since those must come fresh off the actual invoice. "Export to Excel" (`low_stock_export`) exports exactly the checked ids, falling back to the low/out-of-stock predicate only when nothing was explicitly checked.
- **New Purchase's product picker has a "quick add" escape hatch for a part that isn't in the catalog yet** (`POST /products/quick-add`, `routes/products.py::quick_add`) — a modal (minimal fields: part no/name/brand/vehicle/category/unit, no pricing) creates the product via JSON instead of leaving the purchase form. It only appears while a row's search has no match, via a small addition to the shared `searchable-select.js` contract — see [.claude/skills/ui-visual-conventions/SKILL.md](.claude/skills/ui-visual-conventions/SKILL.md) if extending this to another picker (e.g. the Sales form).

**Forms are plain HTML + `request.form`, not Flask-WTF form classes.** CSRF protection is global (`CSRFProtect` in `extensions.py`), but every `<form method="post">` must manually include `<input type="hidden" name="csrf_token" value="{{ csrf_token() }}">` — nothing adds this automatically, including forms that are just a delete button in a list template. Missing this causes a 400 on submit.

**Two different notions of "when" — don't conflate them.** `Purchase.date`/`Sale.date`/`StockMovement.date`/`Payment.date` are user-editable *business* dates (date-only, backdatable, what prints on an invoice) — these are what the Purchases/Sales **list and view/invoice pages** show for "Date" (plain `date.strftime('%d-%m-%Y')`, no `ist()` needed since it's already date-only, not a UTC timestamp), and what `ServerTable`'s Date column sorts/filters on (`Purchase.date`/`Sale.date` directly, plus `date_filter_expr()` for substring search — see `routes/server_table.py`). `created_at` columns are a separate, non-editable server timestamp (`datetime.utcnow()`, set once) — secondary detail rows that log *when an action was actually taken* (Payment History rows, Returns History rows, the Stock Ledger) still show this via the `ist(dt, fmt="%d-%m-%Y %I:%M %p")` Jinja helper (`app.py::inject_ist_helper`), since IST (UTC+5:30, no DST) is what the shop owner actually reads. Don't display `created_at` raw (it's naive UTC, will read ~5.5 hours off local time). (Earlier versions of this doc said Purchases/Sales list & invoice "Date" should show `created_at` instead — that was wrong: a backdated purchase/sale showed today's date everywhere instead of the date actually entered on the form. Fixed.)

**Dates from HTML `<input type="date">` come in as ISO strings and must be converted with `date.fromisoformat(...)` before assigning to a `db.Date` column** (e.g. `Purchase.date`, `Sale.date`, `StockMovement.date`) — SQLite's date type raises `TypeError` on raw strings at insert/update time. Filtering/comparing an existing `Date` column against a plain ISO string in a `WHERE` clause (as `routes/stock.py` and `routes/reports.py` do for date-range filters) works fine and does not need this conversion.

**Deletion guards.** Products/Suppliers/Customers/Mechanics cannot be deleted if referenced by any Purchase/Sale line item — each `delete_*` route checks for this and flashes an error instead of relying on DB foreign-key enforcement (SQLite FKs aren't enforced by default here).

**CSV export / DB backup** (`routes/settings.py`) — `EXPORTABLE` dict maps table name → `(model, [columns])`; add new exportable tables there. Backup just serves `instance/erp.db` directly as a file download.

**Excel mirror** (`excel_sync.py`) — `sync_to_excel()` rewrites `instance/erp_data.xlsx` (one sheet per table) from the current DB state and must be called after every mutating commit (every route that changes data already does this — follow the pattern when adding new ones). `SHEETS` maps sheet name → `(model, [columns])`; columns not present as a real attribute on the row fall back to `_DERIVED` (e.g. `product_name` resolved via a `.product` relationship) — keep this fallback-only, since checking `_DERIVED` before the row's real attributes was a real bug (broke the `Products` sheet, where `product_name` *is* a real column on `Product` itself, colliding with the same key used to mean "look up product name via relationship" on other sheets). **`excel_sync.py::build_ranged_workbook(date_from, date_to)`** is a separate, standalone workbook builder (same `SHEETS` shape) backing `/settings/export/excel-range` — it narrows only the transactional sheets (Purchases, PurchaseItems, PurchaseCharges, Sales, SaleItems, StockMovements, Payments, SaleReturns, SaleReturnItems) to the given date range via `_ranged_filters()`; master/catalog data (Products, Suppliers, Brands, Customers, Mechanics, the two BrandDiscount tables, ShopSettings) is always included in full since it isn't tied to a date. It builds entirely in memory and is never written to `instance/erp_data.xlsx` or fed into the cloud backup — the canonical on-disk mirror must always reflect full current state, so a date-scoped download has to stay a separate on-demand path rather than a variant of `sync_to_excel()`.

**Report exports** (`routes/reports.py`) — every report under `/reports/*` that isn't a single always-current snapshot (i.e. everything except the Reorder report, which already had its own checkbox-driven export) has a sibling `<name>_export` route returning an `.xlsx` built from the exact same query/aggregation logic as the page, via a shared `_send_excel(sheets, filename)` helper (`sheets` = list of `(title, headers, rows)` tuples, one openpyxl sheet each). To keep the view route and its export route from duplicating aggregation logic (a real risk of the two drifting out of sync), each report's data-building code lives in a `_compute_*()` function called by both — e.g. `_compute_contact_detail()` backs both `customer_detail`/`mechanic_detail` (render) and `customer_detail_export`/`mechanic_detail_export`. Filenames run through `_safe_filename()` when they embed user data (a contact/product/brand/supplier name) since this app runs on Windows, which rejects `\/:*?"<>|` in a filename.

**Cloud backup piggybacks on `sync_to_excel()`** — `excel_sync.py::_backup_to_cloud()` runs at the end of every `sync_to_excel()` call and copies both `erp.db` and `erp_data.xlsx` into `Config.CLOUD_BACKUP_DIR` (set via `.env`, e.g. a Google Drive Desktop/OneDrive folder) if that setting is non-empty and the folder currently exists — silently skipped otherwise (offline, not configured, cloud client not signed in), never raises, never flashes. It writes each file to a `.tmp` name in the backup folder and `os.replace()`s it into place, deliberately never writing directly into a live-synced folder mid-copy (a sync client can corrupt a SQLite file it catches mid-write). **Any QA/test server against a copied DB must also neutralize `CLOUD_BACKUP_DIR`** (leave it unset, or point it at a scratch folder) — otherwise a QA session's throwaway data gets copied into the real cloud backup right alongside genuine shop data. `excel_sync.py::cloud_backup_status()` (`{configured, connected, dir, last_synced}`) reads back that same state for display — `connected` just means the folder is currently reachable (`os.path.isdir`), not that the cloud client has finished uploading; `last_synced` is the backed-up `erp.db` copy's own mtime, not separately tracked. Surfaced in two places: a dashboard banner (`routes/dashboard.py`, warning only when `configured` but not `connected` — silent if the feature isn't set up at all, to avoid nagging installs that don't use it) and `routes/settings.py::cloud_backup`/`cloud_backup_sync_now` (`/settings/cloud-backup`, status page + a manual "Sync Now" button that just calls `sync_to_excel()` again — not a separate code path).

## Data notes

- `instance/erp.db` is gitignored (per-shop data, never commit it).
- Auth is a single shop-owner account; `routes/auth.py` redirects to `/auth/setup` to create it if `User.query.count() == 0`, otherwise to `/auth/login`.
- Profit-margin report (`routes/reports.py::profit_margin`) uses the actual batch's `purchase_price` (via `SaleItem.purchase_item`) as cost when known — accurate historical cost, not the product's current cost. Only falls back to the product's *current* `actual_discounted_price` for sales made before batch tracking existed (`purchase_item_id` is `None`).
